# CodeInsight Canonical Semantic Model

CodeInsight is a Windows-first C/C++ semantic-model builder. It consumes one or more authoritative `compile_commands.json` files, asks Clang/libclang to parse the selected translation units, canonicalizes declarations and definitions across translation units, resolves and validates relationships, and publishes a durable SQLite semantic snapshot.

The snapshot is the product. CodeInsight is designed to preserve compiler evidence and provenance rather than produce a best-effort text report. It can therefore tell consumers which translation unit, configuration, declaration, or definition supports a fact. The optional dead-code analysis is a conservative consumer of that model; it is not a replacement for a complete C++ compiler or a guarantee that every runtime path has been discovered.

This repository is an advanced prototype/early MVP. Read [shortcomings.md](shortcomings.md) before relying on the tool for production decisions.

## What the application does

The command-line executable is named `codeinsight.exe`. Its main workflow is:

1. Start with a compiler-generated compilation database.
2. Extract compiler-backed facts from the translation units listed in that database.
3. Merge equivalent declarations and definitions into canonical entities.
4. Validate identity, ownership, relationship, configuration, and persistence invariants.
5. Atomically publish a SQLite model that can be inspected, queried, exported, or consumed by the optional analysis library.

The application supports:

- semantic model construction from one or more compilation databases;
- incremental rebuilds and durable extraction checkpoints;
- strict publication with `--require-complete`;
- model validation and CLI inspection;
- observation-level and deduplicated semantic exports;
- relationship queries and diagnostics;
- conservative dead-code analysis when the analysis component is enabled;
- C++ library targets for clients that need to embed the core model pipeline.

## Prerequisites

### To run the prebuilt Windows package

- Windows x64.
- A project with a valid `compile_commands.json` generated by a supported compiler/build system.
- Sufficient permissions to read the source tree, compilation database, compiler headers, and output directory.
- The matching `libclang.dll` must remain beside `codeinsight.exe`. The shipped archive already contains both files in the same directory; do not separate them.

### To build from source

- Visual Studio with the Desktop development with C++ workload and a native x64 toolchain. The repository has been validated with the Visual Studio 2026 generator; Visual Studio 2022 with a compatible C++ toolchain may work but is not the primary validated environment.
- CMake 3.24 or newer.
- LLVM/Clang 20 or newer with libclang. The current validated toolchain is LLVM/Clang 22.1.x.
- Python 3 when running the verification-enabled test suite. Python is not needed for ordinary model construction or for the core-only CTest suite.
- Git if you are cloning the repository or want to commit the generated distribution archive.

Check the tools before configuring:

```powershell
cmake --version
clang --version
python --version
```

On Windows, CMake searches versioned LLVM installations below `C:\Program Files\LLVM` and selects the newest suitable installation. To select another installation explicitly, pass its root directory during configuration:

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64 `
  -DCODEINSIGHT_CLANG_ROOT="C:\Program Files\LLVM"
```

The configured Clang major version must meet `CODEINSIGHT_MINIMUM_CLANG_MAJOR`, which defaults to 20.

## Use the shipped Windows ZIP

The repository distribution artifact is:

`dist/CodeInsight-1.0.0-windows-x64.zip`

This archive is intentionally **not ignored by `.gitignore`**, so it can be committed to Git and shipped with a repository release. It contains the Release executable, the matching `libclang.dll`, this README, `shortcomings.md`, and the supporting documentation directory. Keep `codeinsight.exe` and `libclang.dll` together after extraction.

Example installation and smoke test:

```powershell
Expand-Archive .\dist\CodeInsight-1.0.0-windows-x64.zip `
  -DestinationPath .\CodeInsight-1.0.0-windows-x64
Set-Location .\CodeInsight-1.0.0-windows-x64
.\codeinsight.exe toolchain
```

The `toolchain` command should report the configured Clang version, runtime Clang version, major version, and whether the version is supported. The archive does not include a C++ project or compilation database; those remain inputs supplied by the user.

## Build from source

From the repository root, configure and build the default configuration:

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64
cmake --build build --config Release --parallel 4
ctest --test-dir build -C Release --output-on-failure
```

The Release executable is written to `build\Release\codeinsight.exe`. On Windows, the build copies the selected LLVM runtime to `build\Release\libclang.dll`. The DLL is copied beside the executable deliberately so that the executable uses the configured runtime rather than accidentally loading an older DLL from `PATH`.

### Build without the analysis consumer

`codeinsight_core` contains extraction, canonicalization, call resolution, validation, export, and persistence. The separate `codeinsight_analysis` library contains dead-code analysis. To produce a semantic-only build:

```powershell
cmake -S . -B build-core -G "Visual Studio 18 2026" -A x64 `
  -DCODEINSIGHT_BUILD_ANALYSIS=OFF
cmake --build build-core --config Release --parallel 4
ctest --test-dir build-core -C Release --output-on-failure
```

The semantic-only executable still supports `build`, `validate-model`, `inspect`, `toolchain`, `export`, `query`, and `diagnostics`. It does not provide the `analyze` command.

### Select a different Clang installation

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64 `
  -DCODEINSIGHT_CLANG_ROOT="D:\toolchains\llvm"
```

The configured Clang major version must meet `CODEINSIGHT_MINIMUM_CLANG_MAJOR`, which defaults to 20.

## Prepare a compilation database

CodeInsight does not invent compiler flags. It relies on the exact commands used to compile the project. Generate `compile_commands.json` with the target project’s build system.

For a CMake project:

```powershell
cmake -S C:\src\sample-project -B C:\src\sample-project\build `
  -G "Visual Studio 18 2026" -A x64 `
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build C:\src\sample-project\build --config Release
```

The resulting database is normally at `C:\src\sample-project\build\compile_commands.json`. Confirm that its commands refer to source files, include directories, defines, language modes, compiler paths, and generated headers that are still available. A database generated for a different machine or configuration can produce incomplete or invalid extraction.

## Command reference and examples

Run the executable from its directory, or use an absolute path:

```powershell
$ci = "C:\tools\CodeInsight-1.0.0-windows-x64\codeinsight.exe"
```

If you built from source instead:

```powershell
$ci = "C:\path\to\codeinsight_ASTRA\build\Release\codeinsight.exe"
```

### Build a semantic model

```powershell
& $ci build `
  --workspace C:\src\sample-project `
  --compile-commands C:\src\sample-project\build\compile_commands.json `
  --output C:\src\models\sample-project.db `
  --jobs 4
```

Important options:

- `--workspace` — source workspace used to resolve and validate paths.
- `--compile-commands` — authoritative compilation database; repeat it to combine configurations.
- `--output` — SQLite model path. Its parent directory is created when possible.
- `--jobs` — extraction worker count. Start with the number of physical cores or less when memory is constrained.
- `--clean` — discard the existing output model and rebuild from an empty model.
- `--require-complete` — reject publication if warnings, partial translation units, failed translation units, or an empty model are present.
- `--project-root` — add a source root when the workspace is not the only relevant root. Repeatable.
- `--entry-root` — mark a configured entry root for consumers such as dead-code analysis. Repeatable.
- `--target` and `--target-kind` — describe a selected link target when the input is partitioned by target.
- `--target-manifest` — partition an umbrella compilation database into authoritative link targets.

Use quotes around Windows paths containing spaces:

```powershell
& $ci build `
  --workspace "C:\Users\Example User\src\sample" `
  --compile-commands "C:\Users\Example User\src\sample\out\compile_commands.json" `
  --output "C:\Users\Example User\models\sample.db"
```

### Combine multiple configurations

```powershell
& $ci build `
  --workspace C:\src\sample-project `
  --compile-commands C:\src\sample-project\build-debug\compile_commands.json `
  --compile-commands C:\src\sample-project\build-release\compile_commands.json `
  --output C:\src\models\sample-project-all-configs.db `
  --jobs 6
```

For a strict publication suitable for downstream automation:

```powershell
& $ci build `
  --workspace C:\src\sample-project `
  --compile-commands C:\src\sample-project\build-release\compile_commands.json `
  --output C:\src\models\sample-project-release.db `
  --require-complete
```

Strict completion means that the selected translation units passed the configured publication gates. It does **not** mean that every C++ call, alias, lifetime, virtual dispatch path, or runtime behavior has been modeled completely.

### Partition an umbrella database with a target manifest

Create `C:\src\sample-project\codeinsight-targets.txt`:

```text
target app executable
entry project::main
root C:\src\sample-project\src

target test executable
entry project::test_main
root C:\src\sample-project\tests
```

Then run:

```powershell
& $ci build `
  --workspace C:\src\sample-project `
  --compile-commands C:\src\sample-project\build\compile_commands.json `
  --target-manifest C:\src\sample-project\codeinsight-targets.txt `
  --output C:\src\models\sample-project-targeted.db
```

See [COMPILATION_MODEL.md](docs/COMPILATION_MODEL.md) for manifest semantics and target ownership rules.

### Validate and inspect a model

```powershell
& $ci validate-model --model C:\src\models\sample-project.db
& $ci inspect --model C:\src\models\sample-project.db
& $ci toolchain
```

`validate-model` checks schema, foreign keys, semantic invariants, and round-trip persistence. `inspect` prints a compact summary, including model counts and call-target completeness. `toolchain` reports the configured and runtime Clang versions.

### Export records or JSON Lines

```powershell
& $ci export `
  --model C:\src\models\sample-project.db `
  --view semantic `
  --format records `
  --output C:\src\models\sample-project-semantic.txt

& $ci export `
  --model C:\src\models\sample-project.db `
  --view observations `
  --format jsonl `
  --output C:\src\models\sample-project-observations.jsonl
```

Observation exports retain translation-unit-owned evidence. Semantic exports deduplicate equivalent relationships while retaining evidence counts and supporting configurations.

### Query relationships and view diagnostics

```powershell
& $ci query `
  --model C:\src\models\sample-project.db `
  --relationship Calls `
  --view semantic

& $ci diagnostics --model C:\src\models\sample-project.db
```

Other relationship names depend on the model schema. Use `inspect` and the contract documentation to identify available relationships and ownership semantics.

### Run conservative dead-code analysis

The default build includes the analysis consumer:

```powershell
& $ci analyze `
  --model C:\src\models\sample-project.db `
  --analysis dead-code `
  --format records `
  --output C:\src\models\sample-project-dead-code.txt
```

Dead-code analysis is intentionally conservative. Configuration variants, templates, exports, configured roots, process entries, address escapes, virtual candidates, incomplete translation units, unresolved calls, target closure, and external linkage can all affect reachability and confidence. Treat the result as a review aid, not as permission to delete code automatically.

## Incremental builds and recovery

If the output snapshot already exists, `build` performs an incremental update. During extraction, CodeInsight writes a durable `<output>.checkpoint` snapshot after every 64 translation units and after the final extraction batch. The checkpoint is transactionally written and checked with SQLite quick and foreign-key validation; it never replaces the final output directly.

If extraction is interrupted or a publication gate rejects the result, rerun the same command **without** `--clean`:

```powershell
& $ci build `
  --workspace C:\src\sample-project `
  --compile-commands C:\src\sample-project\build\compile_commands.json `
  --output C:\src\models\sample-project.db `
  --jobs 4
```

CodeInsight loads the newest usable snapshot and extracts missing or invalidated translation units. A successful final publication removes the checkpoint. Use `--clean` only when you intentionally want to discard incremental state or when the compilation database represents a materially different project.

## Rebuild and publish the Git-shippable ZIP

The canonical archive is generated from the Release output. Rebuild it after changing source, this README, or the supporting documentation:

```powershell
cmake --build build --config Release --parallel 4

$packageRoot = Join-Path (Get-Location) "dist\staging\CodeInsight-1.0.0-windows-x64"
$zipPath = Join-Path (Get-Location) "dist\CodeInsight-1.0.0-windows-x64.zip"

New-Item -ItemType Directory -Force -Path $packageRoot | Out-Null
Copy-Item "build\Release\codeinsight.exe" $packageRoot
Copy-Item "build\Release\libclang.dll" $packageRoot
Copy-Item "README.md" $packageRoot
Copy-Item "shortcomings.md" $packageRoot
Copy-Item "docs" $packageRoot -Recurse
Compress-Archive -Path (Join-Path $packageRoot "*") -DestinationPath $zipPath -CompressionLevel Optimal -Force
Remove-Item -LiteralPath (Join-Path (Get-Location) "dist\staging") -Recurse -Force
```

Verify the result before committing it:

```powershell
Get-Item .\dist\CodeInsight-1.0.0-windows-x64.zip
tar -tf .\dist\CodeInsight-1.0.0-windows-x64.zip
```

The archive should contain `codeinsight.exe` and `libclang.dll` at its top level. The generated ZIP is intentionally trackable in Git; intermediate build directories, object files, DLLs, EXEs, logs, databases, and staging files remain ignored.

## Supported limits and operational cautions

- CodeInsight is Windows-centric and has not established equivalent behavior on non-Windows platforms.
- A successful strict build means the selected translation units met the configured publication gates; it is not a proof of complete C++ semantics.
- Indirect calls, aliases, parameters and returns, registries, member-function pointers, closures, virtual dispatch, lifetime handling, and other broader C++ semantics have known gaps.
- The whole semantic model is held in memory during important phases, so very large projects may require substantial RAM and have not been proven at million-line scale.
- Input paths and source files are not sandboxed. Do not process untrusted repositories without applying an appropriate external isolation policy.
- Keep model outputs and checkpoints outside source directories when possible. SQLite databases and checkpoints are generated artifacts and are ignored by the repository rules.

## Exit status and troubleshooting

For automation, treat a zero exit status as success. A non-zero result means the command failed, the model was rejected, or the requested optional component is unavailable. When a command fails:

1. Run `codeinsight toolchain` and confirm that the configured and runtime Clang versions match and are supported.
2. Confirm that every `--compile-commands` path exists and is valid JSON.
3. Confirm that source files, compiler binaries, include directories, and generated headers referenced by the database still exist.
4. Run `validate-model` and `diagnostics` against the last usable model when recovery is involved.
5. If the complete gate rejects the build, inspect diagnostics before deciding whether to rerun without `--require-complete`.
6. If the executable starts but cannot load libclang, restore `libclang.dll` beside the executable or rebuild the package; do not rely on an unrelated DLL on `PATH`.

For deeper semantic behavior, consult the contract and architecture documents linked above. For known project-level limitations, consult [shortcomings.md](shortcomings.md).
